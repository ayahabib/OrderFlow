# PRD: منصة استخراج الطلبات وإدارة المتاجر بالذكاء الاصطناعي

> النسخة 0.3 (مسودة). تم حسم القرارات الأساسية بالقسم 9، والأسئلة المتبقية بالقسم 10.

## 1. نظرة عامة

### المشكلة
أصحاب المتاجر الصغيرة والمتوسطة بيستقبلوا عشرات أو مئات الطلبات على واتساب وإنستغرام (ورسائل شات)، وبيضطروا:
- يدخلوا الطلبات يدوياً.
- يراجعوا المخزون يدوياً.
- يأكدوا الأسعار والعناوين.

النتيجة: أخطاء، تأخير، وضياع طلبات.

### الحل
منصة ويب بتستقبل رسائل العملاء عبر قناة مراسلة (WhatsApp هي القناة المستهدفة، و Telegram + محاكي ويب للتطوير والعرض)، وبتفهمها تلقائياً، وبتحولها لطلب منظم، وبتتحقق من المخزون، وبترد على أسئلة العميل، وبتحول لصاحب المتجر أي سؤال ما بتعرف جوابه أو أي حالة حساسة.

### النتيجة القابلة للقياس
- تقليل الوقت اللازم لتسجيل الطلب الواحد مقارنة بالإدخال اليدوي.
- تقليل نسبة أخطاء التسجيل (اسم المنتج، الكمية، العنوان).
- نسبة الأسئلة الي جاوبها البوت بدون تحويل لصاحب المتجر.

## 2. المستخدمون

| المستخدم | الوصف | شو بيعمل بالنظام |
|---|---|---|
| صاحب المتجر (Store Owner) | بيدير متجر صغير أو متوسط (مستخدم واحد لكل متجر) | بيسجل دخول، بيرفع المخزون، بيتابع الطلبات والتقارير، بيجاوب الأسئلة المحولة، بيوقف البوت على محادثة |
| العميل (Customer) | بيشتري من المتجر | بيراسل المتجر على واتساب (أو تيليجرام/ويب بالتطوير): بيسأل، بيطلب، بيأكد |

## 3. نطاق المشروع

### داخل الـ MVP
1. تسجيل دخول صاحب المتجر (Auth).
2. عزل بيانات كل متجر (Multi-tenancy).
3. رفع المخزون من ملف Excel/CSV (مع دعم الألوان والمقاسات كـ Variants).
4. بنية **Channel Adapter** موحدة + ربط قناة Telegram ومحاكي شات ويب.
5. استخراج الطلب من رسالة العميل إلى JSON منظم.
6. مطابقة المنتجات مع المخزون وفحص التوفر.
7. صفحة الطلبات (جدول + حالة الطلب).
8. **قواعد تحويل إجبارية** لصاحب المتجر (انظر 4.11).
9. **إيقاف الرد الآلي** على محادثة معينة.

### المرحلة 2
10. شات بوت بيرد على الأسئلة من بيانات المتجر (RAG).
11. تحويل الأسئلة الغير معروفة لصاحب المتجر مع الإشعار وتاريخ المحادثة.
12. تعلّم البوت من إجابة صاحب المتجر (Knowledge Base).
13. ربط **WhatsApp Cloud API** (رقم تجريبي بالتطوير).

### المرحلة 3
14. صفحة المخزون مع Dashboard وتقارير مبيعات مرئية.
15. تعديل المخزون عن طريق شات مع البوت داخل الويب.
16. التنبؤ بالمنتجات الي قاربت تنفد.
17. اكتشاف الطلبات المتكررة والمعلومات الناقصة.
18. رابط لمتابعة حالة الطلب للعميل.
19. Evaluation: اختبار كل نسخة من البوت على محادثات من أرشيف المتجر ومقارنتها بردود الموظف.

### خارج النطاق (حالياً)
- إنستغرام وفيسبوك (ممكن لاحقاً عبر نفس الـ Channel Adapter).
- الدفع الإلكتروني.
- تطبيق موبايل.
- الربط المباشر بقواعد بيانات خارجية للمتجر (فقط Excel/CSV بالبداية).
- المكتبات غير الرسمية لواتساب (مخالفة لشروط الخدمة).

## 4. المتطلبات الوظيفية

### 4.1 تسجيل الدخول وإدارة المتجر
- صاحب المتجر بيسجل حساب ويسجل دخول (مستخدم واحد لكل متجر).
- كل حساب مرتبط بمتجر واحد (اسم المتجر، رقم التواصل، العملة، المنطقة الزمنية).
- بيربط المتجر بقناة مراسلة (Telegram Bot Token، أو بيانات WhatsApp Cloud API).
- بيربط حساب Telegram الخاص فيه لاستقبال الإشعارات.

### 4.2 رفع المخزون
- رفع ملف Excel/CSV فيه أعمدة: اسم المنتج، السعر، الكمية المتوفرة، (اختياري) اللون، المقاس، سعر خاص بالـ variant، SKU، الوصف والتصنيف.
- الصفوف الي لها نفس اسم المنتج بتنجمع تحت منتج واحد، وكل صف بيصير Variant (مثلاً "أحمر / M") وله كمية خاصة فيه.
- المنتج بدون ألوان/مقاسات بيكون إله Variant واحد "الافتراضي".
- عرض معاينة قبل التأكيد، مع رسائل خطأ واضحة لو الملف ناقص أو غلط.
- كل بيانات المتجر المرفوعة بتصير مصدر معلومات للبوت.
- كل تغيير بالمخزون بيتسجل بجدول حركات (inventory movements).

### 4.3 استخراج الطلب
- من رسالة العميل (بالعربي، بلهجات وأخطاء إملائية) بنستخرج: اسم المنتج، الكمية، اللون/المقاس لو موجود، العنوان، رقم الهاتف.
- الـ LLM بيرجع **JSON بصيغة ثابتة** (Structured Output).
- لو معلومة ناقصة (مثلاً العنوان)، البوت بيسأل العميل عنها.
- مطابقة اسم المنتج مع المخزون (تشمل الأسماء المشابهة).
- مطابقة الـ Variant (اللون/المقاس) مع المخزون. لو المنتج إله أكتر من Variant والعميل ما حدد، البوت بيسأله ("أي لون ومقاس؟") ولا بيخمّن.
- الملاحظات الحرة الي ما بتأثر على المخزون ("حار"، "بدون بصل") بتنحفظ كـ notes على بند الطلب.

### 4.4 تأكيد الطلب وفحص المخزون
- قبل التأكيد البوت بيعرض ملخص الطلب (المنتجات، الكميات، السعر الإجمالي، أجرة التوصيل، العنوان).
- **كل الأسعار والمجاميع وأجرة التوصيل بتنحسب بالكود، مش من نص الـ LLM.**
- لما العميل يأكد، النظام بيفحص مخزون كل Variant بالطلب.
- **قاعدة أساسية:** فحص المخزون بيتم بـ **SQL query** (تحديث ذري)، مش بالـ LLM.
- لو المنتج متوفر: الطلب بينحفظ بحالة "جديد" والمخزون بينقص.
- لو مش متوفر: البوت بيبلغ العميل وبيقترح بدائل أو كمية أقل.

### 4.5 الشات بوت (المرحلة 2)
- بيجاوب أسئلة العميل (أسعار، توفر، سياسة التوصيل، أوقات الدوام...) من بيانات المتجر فقط (RAG).
- إذا ما لقى جواب بثقة كافية، بيحول المحادثة لصاحب المتجر.
- ممنوع يخترع معلومات مش موجودة ببيانات المتجر.

### 4.6 التحويل لصاحب المتجر والتعلّم (المرحلة 2)
- لما البوت بيحول، صاحب المتجر بيوصله **إشعار على Telegram** مع **تاريخ المحادثة كامل**.
- صاحب المتجر بيجاوب من الويب، والجواب بيوصل للعميل.
- مع كل جواب خيارين:
  - **"احفظ هالجواب للبوت"**: بيتخزن (السؤال + الجواب) بالـ Knowledge Base للمتجر.
  - **"جواب خاص بهالعميل بس"**: ما بيتخزن (مثلاً خصم خاص لعميل معين).
- المرة الجاية لما يجي سؤال مشابه، البوت بيجاوب لحاله.

### 4.7 صفحة الطلبات
- جدول فيه: رقم الطلب، العميل، المنتجات، الإجمالي، العنوان، التاريخ، الحالة.
- الحالات: جديد، قيد التنفيذ، تم التوصيل، ملغي.
- فلترة (حسب الحالة والتاريخ) وبحث، وتغيير الحالة بنقرة.

### 4.8 صفحة المخزون والتقارير (المرحلة 3)
- جدول المخزون (تعديل مباشر).
- رسومات: المبيعات اليومية/الأسبوعية، المنتجات الأكثر طلباً، المنتجات الي قاربت تنفد.

### 4.9 تعديل المخزون بالشات (المرحلة 3)
- صاحب المتجر بيكتب أوامر طبيعية مثل: "نقّص كمية الفستان الأحمر 5".
- الـ LLM بيحوّلها لـ Function Call، والنظام بينفذها.
- **لازم خطوة تأكيد** قبل أي تعديل ("رح أنقص 5 من الفستان الأحمر، موافق؟").

### 4.10 التنبؤ واكتشاف الأخطاء (المرحلة 3)
- التنبؤ: بالبداية معادلة بسيطة (متوسط المبيعات اليومية ÷ المخزون = أيام متبقية)، وبعدين Time Series Model لو توفرت بيانات.
- طلبات متكررة: تنبيه لو نفس العميل بعت نفس الطلب خلال فترة قصيرة.
- معلومات ناقصة: تنبيه على الطلبات الي ما اكتملت بياناتها.

### 4.11 قواعد التحويل الإجبارية (MVP)
مبنية بالنظام، والبوت **ممنوع يكمل فيها لحاله**، بيحوّل لصاحب المتجر مباشرة:
- العميل طلب يحكي مع شخص.
- شكوى عن طلب أو جودة (البوت بيعتذر وبيجمع التفاصيل وبيحوّل).
- طلب خصم، أو طلبية كبيرة، أو سعر خاص.
- منطقة توصيل مش مسجلة (ما بيعطي أجرة من راسه).
- سؤال عن حساسية أو مكونات المنتج.
- أي معلومة مش موجودة ببيانات المتجر.

### 4.12 إيقاف الرد الآلي
- صاحب المتجر بيقدر يوقف البوت على محادثة معينة ويكتب بنفسه، وبيرجّعه بأي وقت.
- بالمحادثة الموقوفة، البوت ما بيرد ولا بيعدل على طلبات.

## 5. المتطلبات غير الوظيفية

- **الأمان:** مفاتيح الـ API و Bot Tokens بس بـ `.env` أو Secrets، ولا تنرفع على Git.
- **عزل البيانات:** كل جدول فيه `store_id`، وبنستخدم Row Level Security. ملاحظة: الـ backend بيستخدم Service Role لاستقبال رسائل القنوات، فلازم كل query يفلتر بـ `store_id` بالكود كمان.
- **الخصوصية:** بيانات العملاء ما بتنشارك بين المتاجر، والبوت ما بيتعلم إلا الي صاحب المتجر وافق عليه.
- **اللغة:** دعم العربي (لهجات وأخطاء إملائية) والإنجليزي.
- **التكلفة:** اعتماد خدمات مجانية قدر الإمكان.
- **الموثوقية:** أي فشل من الـ LLM لازم ما يضيع الطلب، بيتحول لصاحب المتجر بدل ما يختفي.

## 6. التقنيات

| الجزء | الاختيار |
|---|---|
| Backend | FastAPI (Python) |
| Frontend | React + Vite |
| Database | PostgreSQL على Supabase + pgvector |
| Auth + Storage | Supabase Auth + Storage |
| قنوات الرسائل | WhatsApp Cloud API (مستهدفة)، Telegram Bot API، محاكي شات ويب، عبر Channel Adapter |
| LLM | OpenAI API (الموديل من متغير البيئة `OPENAI_MODEL`) مع Structured Output و Function Calling |

| Dashboard | Recharts |
| الإشعارات | Telegram Bot (رسالة لصاحب المتجر) |

## 7. قياس النجاح

- **دقة الاستخراج:** على مجموعة اختبار (test set) من رسائل طلبات عربية بلهجات مختلفة، نقيس دقة كل حقل (اسم المنتج، الكمية، العنوان).
- **وقت التسجيل:** مقارنة الوقت بين الإدخال اليدوي والتلقائي على نفس مجموعة الطلبات.
- **نسبة الأسئلة المجابة تلقائياً** من إجمالي الأسئلة.
- **نسبة الأخطاء بالمخزون** (طلب اتأكد وهو مش متوفر فعلياً) لازم تكون 0.
- **التحويل الصحيح:** نسبة الحالات الحساسة (شكوى، حساسية، خصم) الي اتحولت فعلاً لصاحب المتجر، لازم تكون 100%.

## 8. المخاطر

| الخطر | الحل |
|---|---|
| الـ LLM بيغلط بالأرقام | الحسابات وفحص المخزون بالكود/SQL فقط |
| الـ LLM بيخترع معلومات | RAG + عتبة ثقة + تحويل لصاحب المتجر |
| البوت بيتعلم معلومات خاصة | خيار "جواب خاص" + موافقة صاحب المتجر |
| تعديل مخزون غلط بالشات | خطوة تأكيد إجبارية |
| حجم المشروع كبير | تقسيم لمراحل وتسليم MVP أولاً |
| ما في بيانات حقيقية للتنبؤ | توليد بيانات تجريبية (synthetic) |
| حدود الخدمات المجانية | مراجعة حدود كل خدمة قبل العرض |
| ربط واتساب محتاج موافقات وتسعير متغير | البدء برقم تجريبي، وتصميم Channel Adapter، ومحاكي ويب كبديل للعرض |
| بيانات عملاء حقيقية مبعوتة للـ LLM بالتطوير | استخدام بيانات تجريبية ومراجعة شروط الاستخدام |

## 9. القرارات المحسومة

1. Backend: FastAPI (Python).
2. LLM: OpenAI API مع Structured Output و Function Calling (بدّلنا من Gemini). مدفوع حسب الاستخدام، فلازم نراقب التكلفة.
3. الإشعارات لصاحب المتجر: عبر Telegram.
4. المستخدمين: مستخدم واحد لكل متجر (بدون موظفين بالـ MVP).
5. القنوات: WhatsApp (Cloud API) هي القناة المستهدفة للمنتج. نطوّر ونختبر على Telegram + محاكي شات داخل الويب، عبر Channel Adapter موحّد.
6. المنتجات: كل منتج إله Variant واحد على الأقل (الكمية والسعر الخاص على مستوى الـ Variant)، والخيارات (لون، مقاس...) بتتخزن مرنة بـ JSON.

7. العملة: عملة وحدة لكل متجر، والافتراضية `ILS`.
8. "الطلبية الكبيرة": تحويل إجباري لو كمية بند واحد ≥ 10، أو مجموع القطع ≥ 20، أو إجمالي الطلب ≥ 1000 (حدود قابلة للتعديل لكل متجر).
9. كشف قواعد التحويل: كلمات مفتاحية بعد توحيد النص العربي (بدون LLM) **أو** حقل `sensitive_reason` من الـ LLM. أي واحد منهم بيكفي للتحويل.
