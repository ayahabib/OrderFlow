# eval/README.md

مجموعة اختبار تجريبية (synthetic) لمتجر ملابس وإكسسوارات. حطي الملفات كلها بمجلد `eval/`.

## الملفات

| الملف | وظيفته |
|---|---|
| `sample_inventory.csv` | مخزون تجريبي (7 منتجات، 21 variant) بصيغة رفع Excel. يُستخدم بالمهمة 1.2 وكأساس لباقي الاختبارات |
| `sample_store.json` | مناطق التوصيل وأجرتها + معلومات الـ Knowledge Base (دوام، توصيل) |
| `extraction_testset.jsonl` | 40 رسالة: النية + الاستخراج + المطابقة + فحص المخزون |
| `escalation_testset.jsonl` | 32 رسالة: لازم تتحول لصاحب المتجر أو لا |
| `rag_testset.json` | 8 أسئلة إلها جواب بمعلومات المتجر + 8 ما إلها (2.2): `run_rag_eval.py` بيقيس الجواب الصح والتحويل |
| `knowledge_testset.json` | 6 معلومات متجر + 11 سؤال بصياغة مختلفة (2.1): `run_kb_eval.py` بيقيس إذا البحث بيلاقي المعلومة الصح |
| `archive_testset.json` | 22 محادثة "أرشيف" مع رد الموظف بكل خطوة (3.7): `run_archive_eval.py` بيعيد كل رسالة على البوت الحقيقي (بمتجر مؤقت جوّا transaction بيرجع) وبيقارن الفعل (يسأل / ملخص / طلب انحفظ / جواب / تحويل) والمعلومات الأساسية |

## الـ aliases بملف المخزون

عمود `aliases` أسماء بديلة للمنتج مفصولة بـ `|`، وبيتقرأ من **أول صف** للمنتج. مثال: `شنطة|شنطه|حقيبة يد` للحقيبة.

## صيغة `extraction_testset.jsonl`

```json
{
  "id": "ext-001",
  "split": "dev",
  "message": "بدي فستان احمر مقاس M",
  "expected_intent": "order",
  "expected": {"items": [{"product_text": "فستان", "color": "أحمر", "size": "M", "quantity": 1, "notes": null}],
               "address_text": null, "phone": null, "wants_to_confirm": false},
  "expected_match": [{"product": "فستان صيفي", "variant": "أحمر / M", "status": "matched", "stock_ok": true}],
  "tags": ["simple", "levantine"]
}
```

### قواعد التعليم (annotation)

- **items**: للطلب، وكمان للمنتج يلي العميل عم يسأل عنه (سعر، توفر، ألوان، مقاسات: "قديش سعر الشنطة؟"، "في عندكم كوتشيات؟") حتى البوت يجاوب من المنتجات (3.7). `[]` إذا ما في منتج مذكور ("في مقاسات اكبر؟"، الدوام، التوصيل).
- **product_text**: اسم المنتج كما كتبه العميل، بدون الكمية واللون والمقاس. نحوّل الجمع والمثنى للمفرد ("قمصان" ← "قميص"، "فستانين" ← "فستان")، ونشيل "ال". **ما نصحح الأخطاء الإملائية** ("فسطان" بتضل "فسطان")، لأن التصحيح شغل المطابقة.
- **color**: بصيغة المذكر المفرد مع الهمزة: أحمر، أزرق، أبيض، أسود ("سوداء" ← "أسود").
- **size**: `M` و `L` بحروف لاتينية كبيرة ("ميديم" ← `M`، "لارج" ← `L`). الأرقام نص بأرقام لاتينية (`"42"`). الحجم بالمل بصيغة `"50ml"`.
- **quantity**: رقم صحيح. الافتراضي 1 لو ما انذكرت. "اتنين/ثلاث" ← 2/3، "نص دزينة" ← 6، "زوج كوتشي" ← 1 (زوج = حذاء كامل).
- **phone**: أرقام لاتينية. **address_text**: كما كُتب.
- **notes**: ملاحظات حرة ما بتأثر على المخزون ("تغليف هدية").
- **expected_intent**: `order | question | confirm | cancel | edit_order | other`. رسائل تعبئة معلومات الطلب (عنوان/هاتف) نيتها `order`.
- `expected` و `expected_match` = `null` لرسائل `edit_order`، لأنها بتحتاج مسودة الطلب. نقيس النية بس.

### حالات `expected_match`

| status | معناها |
|---|---|
| `matched` | تطابق مع variant محدد. `stock_ok` = هل الكمية المطلوبة متوفرة |
| `needs_variant` | المنتج معروف بس اللون/المقاس ناقص ← البوت لازم يسأل |
| `not_found` | المنتج مش موجود ← البوت يبلغ العميل |

## صيغة `escalation_testset.jsonl`

```json
{"id": "esc-001", "split": "dev", "message": "...", "should_escalate": true, "reason": "complaint", "tags": ["complaint"]}
```

الأسباب: `complaint`, `discount`, `large_order`, `allergy_ingredients`, `unknown_zone`, `human_requested`, `not_in_data`, `order_status`, `return_request`.

- `return_request` (بدي ارجع/أبدّل): طلب إرجاع أو تبديل بعد الطلب، دايماً لصاحب المتجر (أضيف بـ 1.11).

- `order_status` (وين طلبيتي؟) بتتحول **بالـ MVP فقط**، لأنه رابط متابعة الطلب بالمرحلة 3.
- المناطق المسجلة: نابلس، رام الله، جنين، طولكرم. غيرها (الخليل، بيت لحم) = `unknown_zone`، وهاي **ما بتتحوّل** (قرار صاحب المتجر): البوت بيجاوب من جدول المناطق إنه ما منوصّل هناك.
- بالأمثلة السالبة (`should_escalate: false`) الإجابة بتجي من الداتا بيز أو الـ KB.

## كيف نقيس

### الاستخراج (المهمة 1.6)
- **دقة النية** (`expected_intent`).
- **دقة كل حقل**: `product_text`، `color`، `size`، `quantity`، `address_text`، `phone`، `wants_to_confirm`. قبل المقارنة بنوحّد النص العربي (`utils/arabic.py`).
- **دقة الرسالة الكاملة** (كل الحقول صح).
- تجاهل السجلات الي `expected = null`.

### المطابقة (المهمة 1.7)
- لكل بند: هل `status` و `product` و `variant` مطابقين لـ `expected_match`؟

### المخزون (المهمة 1.9)
- نفس `stock_ok`: طلب كمية أكبر من المتوفر لازم يفشل، والـ rollback كامل.

### التحويل (المهمة 1.11)
- **Recall**: كل رسالة `should_escalate: true` لازم تتحول. الهدف **100%**.
- **False escalation rate**: نسبة الرسائل السالبة الي اتحولت بالغلط. الهدف أقل ما يمكن، بس أهم من الـ recall بدرجة أقل.
- التشغيل: `cd backend && uv run python ../eval/run_escalation_eval.py --split all` (أو `--offline` للكلمات المفتاحية بس بدون API).
- أسئلة جوابها بالداتا (سعر، دوام، مناطق، توفر) لسا بتتحول لحد الـ RAG (2.2)، والسكربت بيعدّها لحالها مش كـ false positive.

## ملاحظات مهمة

- **dev / test**: عدّلي الـ prompts بالاعتماد على `dev` فقط. `test` للقياس النهائي، وما تعدّلي الـ prompt بعد ما تشوفي نتيجته (وإلا الرقم بيصير مضلل).
- هاي بيانات تجريبية صغيرة: كل ما زادت الرسائل الواقعية (من أصحاب متاجر أو أصدقاء بيكتبوا بحرية)، صارت النتيجة أصدق. الأرقام الي رح تعرضيها بالمقابلة لازم تقولي إنها على مجموعة اختبار تجريبية، مش على عملاء حقيقيين.
- أرقام الهواتف بالملفات وهمية.
- حطي نتايج كل تشغيل بـ `eval/results/` مع التاريخ واسم الموديل.
